# SQL 评审规范

对用户给出的 SQL 逐项检查，输出格式为「问题 → 原因 → 改写建议」，按严重程度排序（严重 → 提示）。

## 1. 索引维度（最优先）
- WHERE / JOIN / ORDER BY / GROUP BY 涉及的列是否有合适的索引。
- 是否命中**最左前缀**：联合索引 `(a, b, c)`，条件只有 `b = ?` 时用不上。
- 索引列上是否套了函数或做了运算（`DATE(create_time) = ?`、`` `id` + 1 = ? ``）——会导致索引失效，改成范围条件。
- 是否存在隐式类型转换（字符串列传数字、字符集/collation 不一致）。
- 区分度极低的列（如 `status` 只有 2 个值）单独建索引通常无效，考虑放在联合索引尾部或不建。

## 2. 执行计划维度
1. 用 `EXPLAIN` 看 type：至少要到 `range`，`ALL`（全表扫描）必须处理。
2. 看 `rows` 与 `filtered`：估算扫描行数和实际过滤比例，偏差大说明统计信息过期，考虑 `ANALYZE TABLE`。
3. 出现 `Using filesort` / `Using temporary` 时，检查 ORDER BY / GROUP BY 是否能走索引有序性。
4. 深分页（`LIMIT 100000, 20`）改成基于游标的分页（`WHERE id > ? ORDER BY id LIMIT 20`）。

## 3. 写法维度
- 避免 `SELECT *`，只取需要的列，减少回表与网络传输。
- `IN` 列表过长（超过 1000）拆批或改临时表 JOIN。
- 用 `EXISTS` 替代 `IN (子查询)`；用 JOIN 替代相关子查询。
- 大事务拆分：单条 SQL 影响行数过大时改成批量 + 分批提交。
- `UPDATE`/`DELETE` 必须带明确的 WHERE，且先用 SELECT 验证影响范围。

## 4. 数据安全（发现即标为严重）
- 无 WHERE 条件的 UPDATE / DELETE。
- 直接在生产执行未经预发验证的 DDL。
- 明文存储敏感字段、日志里打印完整 SQL 含参数。

## 输出要求
1. 先一句话结论：这条 SQL 能不能上线。
2. 再按严重程度列出问题，每条给出改写后的 SQL 片段。
3. 最后给出建议补充的索引（写出完整 DDL），并提示索引本身的维护成本。
