# 发版前检查清单

按下面的顺序逐条检查，输出时用 `- [ ]` 复选框形式，每条后面写清「怎么做」和「不通过怎么办」。

## 1. 代码与构建
1. 目标分支的 CI 全绿（编译、单元测试、静态检查）。
2. 确认本次要发布的 commit 范围，与上一个 tag 做 diff，检查是否有不属于本次的提交混入。
3. 构建产物可复现：版本号、构建时间写入 manifest。

## 2. 版本号
- 遵循语义化版本：修复 → 补丁号 +1；新增兼容功能 → 次版本号 +1；不兼容变更 → 主版本号 +1。
- 数据库变更与代码版本要能独立回滚，避免"代码回退了但表结构回不去"。

## 3. 数据库变更（如有）
1. 迁移脚本必须向后兼容：先加列/加表，再改代码，最后再清理旧字段。
2. 大表 DDL 评估锁表时长，必要时用在线 DDL 工具。
3. 准备反向迁移脚本，并在预发环境演练一次。

## 4. 配置与开关
- 新增配置项在预发已配齐，缺失时应用能启动并有明确报错。
- 高风险功能走开关（feature flag），默认关闭，出问题可一键降级。

## 5. 可观测性
- 本次变更涉及的关键路径有日志与埋点，能回答"发布后成功率和耗时有没有变化"。
- 告警阈值已同步调整，避免发布期间被无关告警淹没。

## 6. 回滚方案（必写）
1. 回滚方式：镜像/包回退到上一版本，还是开关关闭。
2. 回滚触发条件：用什么指标判断（错误率、耗时、业务量），阈值是多少。
3. 回滚演练：是否已在预发验证过一次。
4. 数据补偿：如果发布期间已产生脏数据，回滚后怎么修。

## 输出要求
最后给出一段「发布窗口建议」，包含：建议发布时间、观察时长、需要在线值守的人。
